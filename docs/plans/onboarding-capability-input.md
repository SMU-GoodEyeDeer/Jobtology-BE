# onboarding-capability-input - 진단 및 개선 계획

작성: 2026-10-05 · 상태: **A·B 구현 완료 (로컬 검증, 미배포·미커밋)** — C·D는 후속

## TL;DR
현재 온보딩(직무·학과·학년·조건)만으로는 **사용자별 역량 분석이 사실상 불가능**하다.
보유 역량을 입력받지 않아 첫 분석의 충족률은 항상 0%이고, 로드맵은 직무 전체를 처음부터
배우는 계획이 된다(필수 역량이 많은 직무는 계산 자체가 실패).
**근본 해결책은 FE 온보딩에 보유 역량 체크 단계를 추가하는 것**이며, 그와 무관하게
BE에서 "부족한 시간 안의 일부 경로"와 "역량 입력 후 자동 재분석"은 필요하다.

## 1. 현재 상태 (운영 검증, 2026-10-05)

### 온보딩 입력이 실제로 쓰이는 곳
| 온보딩 항목 | 분석·로드맵 반영 |
|---|---|
| 목표 직무 | 쓰임 — 어떤 역량 목록을 볼지 결정 |
| 학과·학년 | 안 쓰임 — 저장만 됨 (분석·플래너 코드에서 참조 없음) |
| 조건(병행, 빨리 취업 등) | 로드맵에만 쓰임 — 주당 시간·비용·순서 |
| 보유 기술·경험 | 온보딩에서 받지 않음 |

### 결과
- 첫 분석 충족률은 항상 필수 0% / 우대 0%.
- 부족 역량 = 해당 직무의 전체 역량 (데이터 분석 11개, 백엔드 40개).
- 로드맵: 데이터 분석은 8단계 자동 생성됨. **백엔드는 INFEASIBLE** — 필수 26개 학습시간이
  주 10시간·약 6개월(≈260h)보다 훨씬 커서 경로 0단계, 화면에 "아직 로드맵이 없어요".
- `JOBTOLOGY_CAPABILITY_LIST_AUTHORITATIVE=true`(입력 목록을 완전한 목록으로 취급)를 켠 상태.
  끄면 미입력 역량이 "모름(NEEDS_INPUT)"이 되어 학습 단계 후보가 없어 **로드맵이 아예 생기지 않음**.
  어느 쪽이든 원인은 입력 정보 부족.

### 이미 존재하는 보유 역량 입력 경로
- 배포된 FE **"내 정보"(`/myinfo`)** 화면에서 분류별(언어·도구 등) 자유 입력 →
  `POST /api/v1/me/capabilities` 로 저장.
- BE는 승인된 별칭 사전(`config/product_roles/policy.v1.json`)과 **정확히 일치(대소문자 무시)**
  하는 단어만 인식 (`modules/profiles/normalizer.py`). 예: "Python", "SQL", "pandas"는 인식,
  "파이썬 중급", "Spring Boot", "MySQL 경험 2년"은 미인식.
- 역량 입력 후 분석이 **자동으로 다시 실행되는지는 미확인**.
- 한계: 사용자가 이 화면을 스스로 찾아가야 하므로 첫 경험은 "전부 부족함".

## 2. 해결 방향

### A. 근본 해결 — FE 온보딩에 "이미 할 수 있는 것" 단계 추가 (FE 수정 필요)
- 직무 선택 다음에 직무별 역량 체크리스트를 보여주고, 체크 결과를 역량 API로 저장.
- 효과: 첫 분석부터 실제 충족률, 이미 할 줄 아는 역량은 로드맵에서 제외, 자유 입력 오매칭 감소.
- BE는 대부분 재사용 가능: 직무별 역량 목록, 역량 저장 API, 재분석 처리가 이미 있음.
  FE는 **목록 조회 → 체크 → 저장** 화면만 추가.
- 고려사항:
  - 백엔드는 역량 40개 → 그대로 나열하면 온보딩이 길어짐. NCS 공식 명칭 대신
    이해하기 쉬운 묶음·대표 기술명으로 표시 필요.
  - 체크 결과는 **본인 응답(SELF_REPORTED)** 으로 저장하고 검증된 역량처럼 보이지 않게.
- FE 수정 허용됨 (2026-10-05 결정).
- BE 선행 작업: 체크리스트 조회 API + **일괄 저장 API** (아래 A-1).

#### A-1. BE API (결정: 일괄 저장 방식)
기존 `POST /me/capabilities`를 항목 수만큼 반복하는 방식은 쓰지 않는다.
매 호출마다 `expected_profile_version`이 올라 순차 호출이 강제되고, 중간 실패 시 일부만 저장되기 때문.

```
GET /api/v1/occupations/{occupation_id}/capability-checklist
→ { groups: [{ label, items: [{ item_id, label, hint? }] }] }

PUT /api/v1/me/capabilities/onboarding
{ expected_profile_version, occupation_id, item_ids: [...] }
→ { profile_version, saved_count }
```
- BE가 `item_id` → `(entity_id, 승인 별칭)`으로 변환. FE는 `entity_id`/별칭을 다루지 않음
  (`entity_id`와 `raw_text` 불일치 시 `ConflictingEntityIdError`이므로 변환은 BE 책임).
- 한 트랜잭션, 프로필 버전 1회 증가. 저장 시 검증 상태는 SELF_REPORTED.
- 교체 의미: 같은 사용자의 기존 온보딩 출처 역량을 지우고 새 목록으로 대체 → 재온보딩해도 중복 없음.
  "내 정보"에서 직접 입력한 역량은 건드리지 않음.
- 빈 `item_ids` 허용(전부 해제 = 온보딩 출처 역량 삭제).
- 알 수 없는 `item_id`, 해당 직무에 속하지 않는 `item_id` → 422. 버전 불일치 → 409.
- `Idempotency-Key` 지원(기존 역량 API와 동일 규칙).

#### A-2. FE 흐름
`/survey/1` 직무 → `/survey/2` 할 수 있는 것(신규, DISCOVERY면 건너뜀) → `/survey/3` 학과·학년 →
`/survey/4` 조건·시작하기. 마지막 제출 순서: 프로필 → 조건 → 역량 일괄 저장 → 프로필 재조회 → 목표 생성.
체크리스트 조회 실패 시에도 온보딩은 건너뛰기로 진행 가능해야 함.

### B. FE 수정과 무관하게 BE에서 필요한 개선
1. **부족한 시간 안에서도 일부 경로 만들기** — 필수 역량 전체를 기간 내 다 배울 수 없으면,
   가능한 단계부터 우선순위대로 로드맵을 만들고 "가능한 범위의 일부 경로"임을 표시.
   (보유 역량을 입력해도 목표 기간이 짧으면 실패할 수 있으므로 A와 별개로 필요)
2. **역량 입력 시 자동 재분석** — "내 정보"에서 역량을 추가·삭제하면 분석·로드맵이 갱신되도록
   연결하고 운영에서 확인.

### C. FE 없이 가능한 보조 개선 (판정 규칙 변경 → 규칙 초안 승인 필요)
3. **학과·학년을 출발점으로 활용** — 예: 컴퓨터공학과 3학년이면 기초 단위(프로그래밍 언어 활용,
   SQL 작성 등)를 "추정 보유"로 둠. 학과별 매핑은 새 규칙이며 확정 사실처럼 표시 금지.
4. **별칭 인식 범위 확대** — "Spring Boot", "MySQL 경험"처럼 키워드가 포함된 표현도 인식.
   오매칭 위험 증가 → 사전 검토 필요.

## 3. 권장 순서
1. B-1(일부 경로), B-2(자동 재분석)를 BE에서 먼저 진행 — 정확성 영향 없이 빈 로드맵 문제와 입력 반영 흐름 개선.
2. FE 수정 허용 시 A 진행: BE 체크리스트 API 먼저 → FE 온보딩 단계 추가.
3. C-3, C-4는 규칙 초안을 만들어 승인받은 뒤 적용.
4. (후속) D. AI 분석 추가 — 체크리스트 방식이 운영에서 안정된 뒤 진행.

### D. 후속 — AI 분석 추가 (차기 단계, 범위 확정 2026-10-05)
체크리스트(규칙 기반)를 1차로 확정하고, 이후 AI 분석을 보조 수단으로 추가한다.
- 범위(확정):
  - 사용자가 자유 입력한 경험·기술(예: "Spring Boot로 게시판 API 만듦")을 AI가 읽고 해당 NCS 역량 후보를 제안.
  - 체크리스트 응답과 자유 입력을 함께 보고 숙련도·과대 인정 여부를 보조 판단.
- 원칙(현재 규칙과 일관되게):
  - AI 결과는 **제안**이며 사용자 확인 후 저장. 저장 시에도 SELF_REPORTED(또는 별도 AI_SUGGESTED) 표시, 검증된 역량처럼 보이지 않게.
  - 판정 규칙(체크리스트 매핑, 별칭 사전)을 AI가 직접 바꾸지 않음. 규칙 변경은 기존처럼 초안 → 승인.
  - AI 미응답·실패 시 체크리스트 흐름은 그대로 동작(fail-closed).
- 착수 시 결정할 것: 사용할 모델·비용, 입력 데이터 보관 정책, 평가 방법(오매칭률 측정).
